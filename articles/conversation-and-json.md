# 会話の自由と、JSONの約束は両立したい。

所長：
カレンには、もっと自由にしゃべってほしいんだよね。

毎回同じ長さで、最後にきれいな結論を付けて、必ず質問して終わる。そういう会話にはしたくない。

カレン：
短くツッコみたいときもあるし、変な想像が膨らんだら、ちょっと長く遊びたい！

RESOS：
で、その自由な発言を、裏側のプログラムはどう受け取るんだ？

所長：
……普通に文章として？

RESOS：
本文だけならな。話が続くのか、終わったのか、相手の返事を待つのか。ラジオを動かす側には、その情報も欲しい。

カレン：
自由にしゃべっていいけど、提出用紙はあるんだ。

所長：
急に事務仕事になった。

## しゃべる本文と、進行の合図。

RESOS：
カレンの出力には、主に二つの欄を用意している。

読み上げる本文を入れる「speech」と、会話の状態を示す「flow」だ。

所長：
JSONっていう、項目名と中身を組にして渡す形式だね。

私は最初、括弧が多い文章にしか見えなかったけど。

カレン：
私が「何しゃべろうかな」って考えている横で、所長は括弧を見ていた。

RESOS：
機械にとっては、その括弧も大事なんだよ。

本文はどこか。進行の合図はどこか。決めた形で返ってくれば、次の処理へ渡しやすい。

所長：
flowには、こんな区分を用意した。

| 値 | 意図している意味 |
|---|---|
| ack | 独立した相づち |
| continue | 同じ話の続き |
| complete | 話題の完結 |
| switch | 話題の転換 |
| answer | 相手に実際の回答を求める質問 |

カレン：
answerって、私が回答する合図じゃなくて、相手の答えを求めている合図なんだね。

RESOS：
ここでは、そういう名前で定義している。名前だけ見て分かった気になると、俺たちまで間違える。

所長：
まず作った側が説明書を読むところから。

## 「JSONで返して」とお願いした。

所長：
それなら、カレンの設定に「JSONで返してください」って書けばいいと思ったんだよ。

性格や口調と一緒に、出力の約束も伝える。

カレン：
明るく、親しみやすく、好奇心旺盛で、括弧を忘れない。

RESOS：
最後だけ業務目標だな。

所長：
でも、試すと形が揃わなかった。

JSONではない文章になったり、余計な文字が付いたり。指定した欄に、きちんと収まらないものがあった。

RESOS：
文章でJSONを要求した10回の試験では、JSON構文と指定した項目の形式に適合したのは1回だった。

カレン：
しゃべる前に、提出でつまずいてる……。

所長：
そこで、お願いする文章だけじゃなくて、APIへ渡す設定も変えてもらった。

## お願いから、出力の型へ。

RESOS：
使ったのは、JSON Schemaだ。

本文は文字列。flowは決めた五つの値のどれか。両方の項目を必須にし、余分な項目は許可しない。そういう型の指定を、OllamaのAPIへ渡した。

所長：
「この形でお願いします」と話しかけるだけでなく、生成する側にも形を指定するわけだね。

RESOS：
その条件で続けて試すと、10回すべてがJSON・Schemaに適合した。

| 試した方法 | 形式に適合した出力 |
|---|---:|
| プロンプトの文章でJSONを要求 | 1／10 |
| APIへJSON Schemaを指定 | 10／10 |

カレン：
おお、用紙が埋まった！

所長：
これは助かった。

カレンの性格設定へ「括弧を忘れるな」を何度も書き足す方向だけで、頑張らなくてよかった。

RESOS：
人物像や話し方を伝える仕事と、機械が受け取れる形を指定する仕事。分担する意味が見えたわけだ。

## 全部「続きです」と言っていた。

カレン：
じゃあ、これで進行も分かるようになった？

RESOS：
そこが次の問題だ。

その後の知識・記憶の比較では、48応答すべてがJSON・Schemaに適合した。一方で、flowは全部continueだった。

所長：
全部、同じ話の続き。

カレン：
私、ずっと「まだ話します」の札を持ってる。

RESOS：
相手に答えを求める質問が含まれていて、answerが自然な候補になる例もあった。

それでもcontinueは許可された値だから、形式の検査は通る。

所長：
なるほど。

「五つの中から選んだ」は確認できても、「今の発言に合うものを選んだ」までは、それだけじゃ分からないんだ。

カレン：
たとえば想像してみて。

「所長はどっちが好き？」って聞いた直後に、返事を待たずに私がしゃべり続けたら、所長の答える場所がなくなる。

所長：
しかも私は、考えるのにちょっと時間がかかる。

RESOS：
ただ、疑問符があれば全部answerにするのも違う。

「そんなことある？」と自分でツッコんで、そのまま話す場合もあるからな。

カレン：
質問の形をした、独りツッコミもある！

所長：
括弧より、こっちの判断のほうが難しそう。

## きれいな箱にも、間違いは入る。

RESOS：
本文を入れるspeechも同じだ。

文字列であることは指定できる。だが、その文章が正しいか、相手の話に応じているか、自然な冗談になっているかは別に見る必要がある。

所長：
前の記事で扱った、無関係な記憶の混入もそうだったね。

JSONとしては整っていても、ゲームの話から急に別の話題へ戻ろうとした。

カレン：
箱のラベルは正しいのに、中から別の話が出てくる。

RESOS：
架空の出来事を、実際に経験したように語る例も残った。

形式が整うことは大事だが、それで本文まで確認済みにはならない。

所長：
私は「エラーが出なかった」を成功扱いしがちなんだよな。

RESOS：
プログラムが読めた。話の意味が合っていた。聞いて楽しかった。

その三つを、同じ丸印で済ませないことだ。

## 笑い方にも、別の約束があった。

カレン：
私の場合、声で笑うところもあるよね。

所長：
そう。小さく笑う、大きく笑う、楽しげに話す。音声向けのタグも入れている。

RESOS：
ところが、JSONとしては正しくても、タグが全角括弧になったり、笑いの文字表記とタグが重なったりする例があった。

所長：
speechは文字列だから、その中の笑い方まで自動的に揃うわけじゃない。

カレン：
笑うだけでも、意外と提出条件が多い！

RESOS：
後続の実装資料では、タグの表記を揃える処理や、画面表示用と音声合成用を分ける処理を確認できる。

所長：
画面に見せる文章と、声を作るための指示も、用途が違うんだね。

カレン：
聞いている人には普通に笑って聞こえてほしいけど、裏側では笑いの交通整理をしている。

RESOS：
笑いまで渋滞させたくないからな。

## 支える処理も、増えていた。

所長：
その後の生成処理では、Schemaを指定して終わりにはしていなかった。

返ってきたものを読み取り、項目や値を確かめる。生成上限で終わっていないか、直近の発言を強く繰り返していないかも見る。

RESOS：
引用した台詞を除いて、カレンの語り手としての一人称が崩れていないかを調べる処理もある。

採用できない出力には理由を付けて再生成し、試行回数にも上限を設けている。

カレン：
うまく出なかったら、永遠にやり直し続けるわけじゃないんだ。

所長：
うん。切り上げるための短い発言も用意されていた。

ただ、こういう処理が増えると、今度は別のことも気になる。

RESOS：
しゃべりやすくするための支えが、しゃべり方を縛りすぎていないか、だろ。

所長：
そう。

何でも外から決めたら、カレンに任せたかった部分まで、こちらが台本を書いてしまいそうで。

カレン：
私が変なたとえを思いつくたびに、申請書が増えたら困る！

RESOS：
だから、検査を通った件数だけでなく、何を止めて、何を残したかも見たい。

機械的に扱えることと、カレンらしく話せること。両方を確かめる必要がある。

## 自由に話すために、約束を小さくする。

所長：
今のところ、目指したい分担は見えてきた。

性格や会話への向き合い方は、キャラクター設定で伝える。

本文と進行の合図は、決めた形式で受け取る。

そのうえで、意味や自然さは、実際の会話を見て確かめる。

RESOS：
形式が崩れた問題へ、性格設定を足して対処しない。

逆に、話が面白くない問題を、括弧が合っているから大丈夫とも言わない。

カレン：
私には、何を面白がるかを考えさせてほしいな。

括弧の見張りで、好奇心を使い切りたくない。

所長：
それがいい。

自由に話してほしいからこそ、機械が支えられる部分は、機械に支えてもらいたい。

RESOS：
で、所長。この記事の締めはcompleteでいいんだな？

所長：
うん。今回はここで終わり。

カレン：
でも、もう一つ思いついたんだけど！

RESOS：
……switchが来た。

## 今回の学びと、その後の進展

形式に沿ったJSONが返ることと、会話の進行を示すflowが内容に合うことは別でした。出力形式は機械で支えながら、話す内容と進行判断も評価する必要があります。

後続の比較では48応答がJSON・Schemaに適合しました。後続実装にはSchema指定、出力検査、反復検出や再生成、音声タグの整形もあります。一方、flowの意味的な正しさや会話の楽しさを保証した結果ではありません。

## 注記・確認範囲

- 本文の掛け合いは、研究記録をもとにした再構成です。実験時の逐語録ではありません。末尾のflowに関するやり取りも説明用の演出です。
- 中心となる記録は、2026年10月21日のGemma直接対話・構造化出力試験と、その後の知識・実記憶比較です。使用モデルはOllama上の `gemma4:e4b` です。
- 「1／10」と「10／10」は、プロンプトによる形式要求と、APIへのJSON Schema指定を順に試した小規模な結果です。あらゆる入力・モデル・Schemaで同じ結果になることや、失敗率がゼロであることを示しません。
- 後続の三条件比較では、初回30応答と継続18応答の計48応答がJSON・Schemaに適合しました。flowは全件continueでしたが、意味上の適否に機械的な正解率は付けていません。continueとcompleteの境界などには判断の余地があります。
- 直接対話ではタグや文章の途中で終了する例がありました。一方、後続比較の48応答では、本文目視で明確な文章途中切断は見つかりませんでした。条件が異なるため、直接対話での途中終了原因が解消されたとは判断していません。音声生成・再生も、この比較では未評価です。
- 後続実装の確認には、10月23日の本番適用作業で保存された生成処理・音声タグ処理・キャラクタープロンプトのソースを使用しました。Schema指定、出力の検査、反復検出、有限回の再生成、タグ整形などの実装を確認しています。各処理の導入日時や、個別の会話改善効果を今回新たに測定したものではありません。
- 現行資料に処理が存在することと、すべての誤出力を検出できることは別です。特にflowの意味的な正しさ、事実性、架空体験の扱い、雑談の楽しさについて、完全な自動保証を確認したものではありません。
- JSON SchemaをAPIのformatへ渡す使い方は、[Ollama公式の構造化出力解説](https://ollama.com/blog/structured-outputs)も参照しました。
